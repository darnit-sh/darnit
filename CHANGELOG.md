# Changelog

Notable changes to darnit. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). Before 1.0, a patch release (0.1.x) can add CLI flags, exit codes, report formats and JSON fields but never changes or removes them; that waits for a minor release (0.x.0).

## [Unreleased]

### Added

- `check` lists retired or retiring model names set as a value outside the call under "Possibly affected": a constant, a default, a keyword argument (including framework calls such as LangChain's `ChatOpenAI(model=...)`), an object or dict entry, or an environment variable's default, named for a model or engine. Test files are skipped. `check --json` adds `possiblyAffected`, with the same fields as `hits` plus `model`. These never change the exit code, and `fix` leaves them alone. ([#61](https://github.com/darnit-sh/darnit/pull/61))
- `check` counts every other exact mention of a retired or retiring model name in any file, such as docs, config files, `.env` files, tests and comments, per file under "Also mentioned". `--mentions` lists each line, and `check --json` adds `mentions`, with `id`, `file`, `line` and `model`, and `scanned.otherFiles`, the number of other files searched. Mentions never change the exit code, and `fix` leaves them alone. ([#62](https://github.com/darnit-sh/darnit/pull/62))
- `check` notes calls made with OpenAI's SDK pointed at a local or private network address (such as localhost, 192.168.x or `*.local`), and `--json` gets `localAddresses`. The exit code is unchanged. `fix` lists these as `needs a human` instead of rewriting them, since a local server may not accept the new parameter. ([#39](https://github.com/darnit-sh/darnit/pull/39))
- The pull request footer links the change record on darnit.sh. ([#40](https://github.com/darnit-sh/darnit/pull/40))
- `check` and `fix` end with one line when npm has a newer release line than the one running, such as 0.3 while you run 0.2, naming the version to change in `.github/workflows/darnit.yml`. A newer patch release prints nothing. In GitHub Actions the line is a notice on the run summary. darnit asks the npm registry once per run and waits at most 1.5 seconds; the exit code never changes, and nothing is written to disk. `--json` never asks, nor does a run with Node's proxy support turned on (`NODE_USE_ENV_PROXY` or `--use-env-proxy`), and setting `DARNIT_NO_UPDATE_CHECK` or `NO_UPDATE_NOTIFIER` turns it off. ([#79](https://github.com/darnit-sh/darnit/pull/79))
- `check` reports two more OpenAI changes from OpenAI's API specification: `user` on image edit and generation calls is deprecated in favor of `safety_identifier`, and `spend_control` is no longer accepted on `POST /agents/sessions` and `POST /agents/sessions/{session_id}`, found on raw HTTP calls to those paths with a bare or quoted key. `fix` rewrites neither while both records wait for review: `spend_control` has nothing to rename to, and `user` waits until the SDK versions that accept `safety_identifier` on image calls are confirmed. ([#121](https://github.com/darnit-sh/darnit/pull/121))
- `SECURITY.md` says how to report a security problem privately, which versions get fixes, and what counts. ([#95](https://github.com/darnit-sh/darnit/pull/95))

### Changed

- The workflow `init` writes runs `cd "${RUNNER_TEMP:?}" && npx darnit@0.2 check "${GITHUB_WORKSPACE:?}"`, and `check`, `fix` and `init` take the repository's folder as an optional argument (`darnit check path/to/repo`); an empty path exits 2 instead of reading the current folder. Started inside the repository, npx uses a darnit from the repository's `node_modules` and settings from its `.npmrc`, so a repository could run its own code before darnit started. A workflow written by an earlier version keeps its old line; change it to the new one in `.github/workflows/darnit.yml`. On code you do not trust, run only `check`, from outside the repository, with its path. ([#126](https://github.com/darnit-sh/darnit/pull/126))
- `check` no longer counts a model name that code can also use as a variable, such as `o1`, under "Also mentioned" when a code file uses it as one (`compare(String o1, String o2)`, `var o1=hb` in a bundle). In code files it counts inside a string or a comment or as a setting value; in docs, config and other files every mention still counts. On a line over 5,000 characters, as in a minified bundle, it counts only directly inside quotes or as a setting value. ([#90](https://github.com/darnit-sh/darnit/pull/90))
- The workflow `init` writes runs `npx darnit@0.2` instead of `npx darnit`, so a scheduled run takes fixes but waits for you to move to a new minor release, which can change behavior. A workflow written by an earlier version keeps running the latest release; change `npx darnit` to `npx darnit@0.2` in `.github/workflows/darnit.yml` to pin it. ([#58](https://github.com/darnit-sh/darnit/pull/58))
- The repository's build and test commands run without `GITHUB_TOKEN` and `GH_TOKEN`, and those values are replaced with `***` in any output darnit keeps. A test suite that needs either variable no longer gets it from darnit. ([#41](https://github.com/darnit-sh/darnit/pull/41))
- darnit's git commands no longer run git hooks, including your own (husky, commitlint, pre-push) and a global `core.hooksPath`, since git cannot tell them from hooks a repository's tests planted. Outside GitHub Actions the push uses git's own credentials, the same as your own `git push`; darnit's token only opens the pull request. A credential helper that reads the token from the environment, such as `gh auth setup-git` with only `GH_TOKEN` set, no longer works for that push. ([#43](https://github.com/darnit-sh/darnit/pull/43))
- In GitHub Actions, `fix --pr` hands `GITHUB_TOKEN` (or `GH_TOKEN`) to its own `git ls-remote` and `git push` to github.com, through each command's environment, never on disk or in its arguments. The workflow can then check out with `persist-credentials: false`, which leaves no token in git config or under `$RUNNER_TEMP` for the repository's install scripts and tests to read, and the README workflow now does. A token the checkout saved is replaced for those calls, not sent twice. Without either variable they use git's own credentials, as before. An empty or blank `GITHUB_TOKEN` falls through to `GH_TOKEN`, and either is trimmed, for these calls and for opening the pull request. Git config the repository's own code writes, such as `http.curloptResolve` with `http.sslVerify false`, can still send darnit's git calls to GitHub, and the token with them, to another server, including the branch check that runs before any test; the README workflow cannot prevent this, so on code you do not trust, run `check` only. Output darnit keeps from the build and tests also hides the token in base64, as a git auth header carries it, and the credential on any `Authorization: Basic`, `Bearer` or `token` line. ([#127](https://github.com/darnit-sh/darnit/pull/127))
- darnit's six runtime dependencies are pinned to exact versions, so `npx darnit@0.2` installs the same dependency versions darnit was tested and released with, instead of whatever newer version npm finds that day. Every package they pull in was already pinned exactly. ([#96](https://github.com/darnit-sh/darnit/pull/96))
- The npm package includes `CHANGELOG.md`, so the changes are readable offline in `node_modules/darnit`. ([#59](https://github.com/darnit-sh/darnit/pull/59))
- darnit is tested on Node 26 as well as Node 22 and 24, on Linux and macOS. ([#131](https://github.com/darnit-sh/darnit/pull/131))

### Fixed

- A GitHub token holding anything but printable ASCII inside, such as a space, a line break, a control character, a zero-width space or an accented letter, from `GITHUB_TOKEN`, `GH_TOKEN` or `gh auth token`, is refused with exit code 2 before any request or git call, with a message that says which characters a token may hold and does not include the token. Before, a line break inside put the whole token in the error message. Spaces around the token are still trimmed. An error from a GitHub request also replaces the token with `***` wherever fetch or the server quotes it.
- Text from the scanned repository no longer reaches the terminal, `--json` output or a pull request body with raw characters that can hide or reorder text: Unicode's default-ignorable characters (direction controls such as U+202E and U+2066, zero-width spaces and joiners, tag characters U+E0000 to U+E007F, which can spell text nobody sees, variation selectors, the soft hyphen and Hangul fillers), line separators (U+2028, U+2029) and control characters U+007F to U+009F, such as U+009B, which some terminals read as ESC [. Each one is written out as `\u202e`, or two such escapes above U+FFFF: visible in the terminal and in pull requests, where file names showed `?` or nothing before, and a JSON escape that reads back as the same character. Emoji stay whole: a joiner between two pictographs (families, skin tones), U+FE0F after a pictograph or in a keycap, and the tag letters of the flags of England, Scotland and Wales are kept; any other tag characters are written out. Accents, CJK and other text look the same as before; U+200C, which some scripts use between letters, is now written out too. Test output is written out before it is cut to its last 16,384 characters, so a pull request description stays under GitHub's 65,536-character limit, and `fix --pr` skips a change whose description would still be longer, before pushing anything, and says so. A character of test or build output that reaches darnit split across two reads, such as an accented letter, CJK or an emoji, is kept whole; before, it showed as two U+FFFD.
- The workflow `darnit init` writes, and the `check` and `fix --pr` workflows the README shows, remove the `tsc`, `eslint-stylish` and `eslint-compact` problem matchers that `actions/setup-node` registers, before darnit runs. Matchers read every line of the log and ignore `::stop-commands::`, so before, a line from the repository that darnit prints, such as `src/x.ts(1,1): error TS2322: pwned` in the test output `fix` shows or a crafted file name in the `check` report, became an annotation on the run. A workflow written by an earlier `init` gets the step from `darnit init --force`.
- In GitHub Actions, a line of the repository's test or build output, of the diff `fix` shows, or of a file name or snippet that `check`, `init` or an error message prints, can no longer run as a workflow command such as `::error::`, `::add-mask::` or `::stop-commands::`, which could add annotations, mask values or turn off darnit's own. darnit puts `::stop-commands::` with a new random token before that text and the token after it; the text between them is printed as before. The fence turns on only when `GITHUB_ACTIONS` is `true`, so a run that drops the environment while its output still reaches the runner, such as `sudo npx darnit` or `docker run` without `-e GITHUB_ACTIONS`, is not fenced. It stops workflow commands, not problem matchers: the workflow `init` writes removes the ones `actions/setup-node` adds, but a matcher that another action or a step of a workflow you write yourself registers still turns a line like `src/x.ts(1,1): error TS2322: ...` in the test output into an annotation. `--json` output, which is not fenced, writes `#` as `\u0023`, the same value to any JSON parser, since the runner also reads the older `##[command]` form anywhere in a line.
- `init --force` refuses, with exit code 2 and before writing either file, to overwrite `darnit.yml` or the workflow when git could not put it back: edited, staged, untracked, ignored, changed only in its line endings, or differing from git's name only in case, using the same check as `fix`. The message names the files and says to commit or stash them first. Outside a git repository it refuses to overwrite an existing file and says to move it aside. Before, `--force` replaced the file and an uncommitted edit was lost. A file that already matches what `init` would write is left alone and reported as up to date, in or out of a repository. A committed file with no changes is overwritten as before, and `init` without `--force` is unchanged.
- `fix` and `fix --pr` refuse a bare repository and any folder inside `.git` with exit code 2 and the message "not a checked-out git repository", the same as a folder that is not a repository, which now gets that message too. Before, git's check passed there, so `fix` stopped on a raw git error ("this operation must be run in a work tree") or said "Nothing to fix." A subdirectory of a repository and a linked worktree still work as before.
- `fix` refuses, with exit code 2 and before touching any file, when a file it would rewrite is not committed as it is: untracked, ignored, changed or staged (including only its line endings, when `.gitattributes` makes git convert them), marked `assume-unchanged` or `skip-worktree`, or inside a nested repository or submodule. Before, it rewrote such a file in place, and git had no copy to undo it from. The message names the files and says to commit or stash them first, or preview with `--dry-run`. A file whose name on disk differs from git's only in case, on a disk that ignores case, is refused with a message saying so. `fix --pr` uses the same check, so it now also refuses ignored, `assume-unchanged`, `skip-worktree`, nested repository and submodule files, and names the files.
- `fix`, and the build and test commands it runs, work on the folder it was given even when `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` or another variable git keeps local to a repository (the list `git rev-parse --local-env-vars` prints) is set, as in a git hook or a CI step that exported one. Before, `fix --pr` could commit to and push from that other repository, and a build step such as husky's `prepare` could write that repository's git config. Neither darnit's git commands nor the build and test commands get `GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS` from the environment any more, since git treats those as local to a repository too. This does not keep out all git config from outside the repository: darnit's git commands still read the config files that `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `HOME` and `XDG_CONFIG_HOME` point to.
- `check` finds a field sent with its key in quotes, as raw HTTP code writes JSON bodies: `json={"max_tokens": 100}` in Python and `{ "max_tokens": 100 }` or `{ 'max_tokens': 100 }` in JavaScript, in an SDK call or a request to the change's endpoint. Every change record gets this, including retired model names (`{"model": "gpt-4"}`), which move from "Possibly affected" to call sites when sent in such a request. `fix` reports these and leaves them unchanged. A body built elsewhere and passed in by name is still not checked.
- A change record with a detection pattern ast-grep cannot compile still stops `check` and `fix` with exit 2, but now before scanning, with an error naming the record's file, id and language and saying to upgrade darnit or report it. Before, the scan stopped on the first file of that language with an ast-grep error that named no record. Every pattern is compiled for every grammar it is scanned with when the records load. The fixture runner reports the same error, and also fails a record with patterns or rules in a language no fixture file covers.
- `fix --pr` no longer waits forever on a git remote that stops answering. Over HTTP and HTTPS, checking whether the branch exists on `origin` ends once nothing has arrived for 30 seconds, and the push for 60, with an error naming the git command and exit code 2. A slow push that keeps moving is not cut off, and git settings in the repository or the environment cannot turn the check off. Over SSH or another transport git cannot watch, the command is stopped after four times as long.
- `fix --pr` stops waiting on a GitHub API call that has not answered after 30 seconds and says which one, such as `GitHub GET /repos/o/r timed out after 30 seconds`, with exit code 2. A connection that never comes up now names the call too, such as `GitHub GET /repos/o/r failed: fetch failed (connect ECONNREFUSED ...)`. Before, a stalled connection held the run for about five minutes per call, and both failed with only `fetch failed`. ([#117](https://github.com/darnit-sh/darnit/pull/117))
- `fix` on a branch with no commits yet, such as right after `git init`, refuses before touching any file and says to commit first, exit code 2. Before, it rewrote the files, then failed with a raw git error and left them rewritten without running the tests. `--dry-run` still works there, since it writes nothing. When git fails after the rewrite for any other reason, such as a damaged `.git/index`, `fix` now puts the files back before reporting the error. ([#116](https://github.com/darnit-sh/darnit/pull/116))
- A build or test run that `fix` stopped after 10 minutes is reported as timed out, with the files put back and exit code 1. Before, darnit ran it a second time, another 10 minutes, then said the change broke it or that it was already failing; a build that timed out both times kept the change as "already fails without the change". The same holds when a run fails with the change and then times out without it; before, a build like that kept the change and `--pr` opened a pull request. A run no longer waits past the limit for a process that left its process group and kept the output open. `fix --json` adds `timedOut`, `kind` and `notChecked` to each check. ([#92](https://github.com/darnit-sh/darnit/pull/92))
- `fix` ends with the same "Not checked" lines as `check`, naming folders and files the scan did not read, and says "Nothing to fix in the files darnit checked." instead of "Nothing to fix." when there are any. When `check` lists model names outside the call sites, `fix` says "No call sites to fix." and points to `darnit check`. `fix --json` adds `scanned`, the same as in `check --json`. ([#92](https://github.com/darnit-sh/darnit/pull/92))
- `check` and `init` name what they do not search under "Not checked": dependency and build folders such as `node_modules`, `vendor`, `dist`, `build` and Python virtual environments, copies of an SDK bundled into the project, symbolic links to outside the repository, and folders and files that could not be read. Before, a call in `src/vendor/openai.ts` or in an unreadable file was skipped without a note. `check --json` adds `scanned.skipped`, with each one's `path` and `reason`. When anything was not checked, a clean `check` says "No call sites of known vendor changes found." instead of "No known vendor changes affect this repository." ([#91](https://github.com/darnit-sh/darnit/pull/91))
- File and folder names from the repository, and local addresses written in its code, print on one line in `check`, `fix` and `init`: a line break, any other control character and characters that change text direction show as `?`. A crafted name can no longer add a line to the report, such as a fake result or a GitHub Actions command, and `init` no longer passes one that clears the screen or changes colors. `--json` output is unchanged. ([#91](https://github.com/darnit-sh/darnit/pull/91))
- The shorthand `create({ model, messages, max_tokens })` is found and rewritten. ([#35](https://github.com/darnit-sh/darnit/pull/35))
- A retiring model written as the fallback value is found: `?? "name"` and `|| "name"` in JavaScript and TypeScript, `or "name"` in Python. ([#36](https://github.com/darnit-sh/darnit/pull/36))
- A retiring model is reported as a call site in the calls that set up a realtime session: `beta.realtime.sessions.create`, `beta.realtime.transcription_sessions.create`, `realtime.client_secrets.create`, `realtime.calls.create`, `realtime.calls.accept` and `realtime.translations.client_secrets.create`, with their `with_raw_response` and `with_streaming_response` forms and the JavaScript names (`transcriptionSessions`, `clientSecrets`). In JavaScript a model set inside `session: { model }` is reported too. In Python a model inside `session={"model": ...}` or `session=dict(model=...)` stays under "Possibly affected". ([#94](https://github.com/darnit-sh/darnit/pull/94))
- A retiring model passed to the JavaScript realtime helpers `OpenAIRealtimeWS.create(client, { model })`, `OpenAIRealtimeWebSocket.create(client, { model })` and `OpenAIRealtimeTranslationWS.create(client, { model })` is reported as a call site, with the class imported from `openai/realtime/ws`, `openai/realtime/websocket`, their `openai/beta/realtime/` versions or `openai/realtime/translations/ws`. A class of the same name from another package or defined in your own code is not a call site, and its model stays under "Possibly affected", as does a model passed to `new OpenAIRealtimeWS({ model })` or to a class imported under another name. ([#100](https://github.com/darnit-sh/darnit/pull/100))
- `check` counts a model name made only of letters, such as `ada` or `davinci`, under "Also mentioned" only when it sits inside quotes (`"ada"`, `'ada'`, `` `ada` `` or `\"ada\"` in a JSON string) or is the whole value of a setting named for a model or engine (`OPENAI_MODEL=ada`, `model: ada`), so an agent or person named Ada in a README is no longer counted. Text files over 10 MB that are not JavaScript, TypeScript or Python are named under "Not checked" and in `check --json` `scanned.tooLarge`, like code files, instead of being skipped without a note. A file that grows past 10 MB while it is read is treated the same way. ([#67](https://github.com/darnit-sh/darnit/pull/67))
- A model name listed in more than one change record is reported under each of them, the same way call sites are: under every record's heading in "Possibly affected", and once per record in `possiblyAffected` and `mentions` in `check --json`, each entry with that record's `id`. Before, only one of the records showed it. "Also mentioned" still counts each line once. None of the shipped records share a model name. ([#87](https://github.com/darnit-sh/darnit/pull/87))
- `fix` renames `max_tokens` only in a call's first argument, not in the request settings passed second. `check` still reports one written there, and `fix` leaves it to a human. ([#37](https://github.com/darnit-sh/darnit/pull/37))
- When `package.json`, `pyproject.toml` or `setup.cfg` is there but could not be read (over 10 MB, not a regular file, a broken link, or no permission), `fix` says so and suggests `--test`, instead of reporting that no test script was found. A `package.json` it could not read no longer makes `fix` run pytest instead, or the TypeScript compiler as the build check; `fix` says the build check did not run, and `fix --json` adds `buildNote`. ([#69](https://github.com/darnit-sh/darnit/pull/69))
- A pull request opened with `fix --pr --no-test` says the tests and the build check were skipped with `--no-test`, instead of claiming the repository has no test command. ([#85](https://github.com/darnit-sh/darnit/pull/85))
- Test and build output that `fix` keeps for the pull request and `fix --json` is plain text: color codes, cursor moves and terminal links from tools such as vitest, jest or pytest are removed, so the pull request no longer shows `[32m` and the like. A token broken up by such codes is still replaced with `***`. ([#89](https://github.com/darnit-sh/darnit/pull/89))
- `init` refuses to write `darnit.yml` or the workflow through a symbolic link that leads outside the repository, such as a `.github` folder linked elsewhere, and exits 2 with the file it refused. Before, it wrote the file wherever the link pointed. ([#57](https://github.com/darnit-sh/darnit/pull/57))
- `init --force` writes each file as a new file with the old one's permissions and moves it into place, so a file hard-linked to `darnit.yml` or the workflow, such as one outside the repository, is no longer changed. `init` checks both files and writes both before moving either into place, so a refused workflow or a failed write (such as a read-only `.github/workflows` folder) no longer leaves `darnit.yml` rewritten on its own; a failed write is reported in one line and changes no file. A `setuid` or `setgid` bit is not carried over. A `.github` folder link that points nowhere, or a `.github` that is a file, gets a refusal instead of a raw error, and a `darnit.yml` link is reported as a link instead of an existing file. ([#71](https://github.com/darnit-sh/darnit/pull/71))
- `fix` no longer reads settings files (`sgconfig.yml`) from the repository, which could make it load a library the repository named, even with `--dry-run --no-test`. (#42)
- The repository's tests can no longer plant git hooks or settings that darnit's own git commands then run with its token. File names are passed to git literally, so a file named `*.ts` no longer pulls other files into the commit. ([#43](https://github.com/darnit-sh/darnit/pull/43))
- File names, commands, test output and notes from the repository are shown literally in the pull request body and the terminal, so they cannot add live Markdown, mentions or links to the body, or send codes that change the terminal's title, clipboard or screen. Only the end of long test output is kept. ([#44](https://github.com/darnit-sh/darnit/pull/44))
- `fix --pr` uses the `origin` remote only when github.com is its host, and refuses repository names that could reach another part of GitHub's API with your token. ([#49](https://github.com/darnit-sh/darnit/pull/49))
- A file padded with blank lines or spaces to slow down the patterns darnit matches against it, such as an import split over thousands of blank lines, no longer stalls `check`, `init` or `fix`. A named pipe, such as one named `darnit.yml`, is not opened, so it no longer hangs `check`. Files over 10 MB are not read: `check` and `init` name them under "Not checked", and `check --json` lists them in `scanned.tooLarge`. The exit code is unchanged. ([#60](https://github.com/darnit-sh/darnit/pull/60))
- `fix` no longer hangs or fills memory when `package.json`, `pyproject.toml` or `setup.cfg` is a named pipe or a link to one, or a link to a device such as `/dev/zero`. Like every other file, they are read only when they are regular files under 10 MB. A file replaced by a named pipe while darnit opens it no longer hangs `check`, `init` or `fix`. ([#66](https://github.com/darnit-sh/darnit/pull/66))
- A source file with thousands of SDK clients and calls, calls in functions nested thousands deep, or a Python assignment chained thousands of names long, no longer slows `check` for seconds to minutes. A client name set more than 50 times where one call can see it, such as at the top of one file, is no longer traced, so that call is reported as the vendor's even if it goes to another provider. ([#68](https://github.com/darnit-sh/darnit/pull/68))
- A source file with raw requests or other calls nested thousands deep, or one call with thousands of arguments, no longer slows `check` for seconds to minutes. ([#70](https://github.com/darnit-sh/darnit/pull/70))
- `check` on a source file that sets the same SDK client tens of thousands of times, each just before a call, takes less than half as long. ([#72](https://github.com/darnit-sh/darnit/pull/72))
- `check` parses each file once for all change records instead of once per record, and reads only the parts of the file around what it finds, so a file with thousands of call sites takes far less memory and time: one with 20,000 calls peaked near 2 GB and now stays near 550 MB. The output is unchanged. ([#78](https://github.com/darnit-sh/darnit/pull/78))
- `check --json` writes call sites and model values in pieces, as it already did for mentions, so a report with hundreds of thousands of them no longer holds a second full copy in memory or fails once it passes the longest string Node can hold. The output is unchanged. ([#77](https://github.com/darnit-sh/darnit/pull/77))

## [0.1.0] - 2026-10-07

First release.

### Added

- `darnit init` finds the APIs a repository uses and writes `darnit.yml` and a daily GitHub Actions workflow.
- `darnit check` lists the call sites affected by a known change, with the vendor's own source. `--json` for machine-readable output.
- `darnit fix` rewrites the calls a tested rule covers, checks the result against your SDK version, build and tests, and with `--pr` opens one pull request per change.
- OpenAI supported, with 33 change records, including `max_tokens` to `max_completion_tokens` on chat completions (rewritten), `functions` to `tools` (reported), and retiring models from OpenAI's deprecations page (reported). Anthropic, Stripe and Twilio are recognized by `init`.
- Reads JavaScript, TypeScript and Python.
